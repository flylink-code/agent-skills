# 排查协议

用于：现象定位、缺陷复现、根因分析、硬件/软件联合调试。

## 铁律

1. **不要把"结论"当交付**。交付是"下一步能拿到新信息的动作"。
2. **不要把球踢回去**。禁止以"证据不足，无法确定"收尾；改成取证计划。
3. **一次只改一个变量**。同时动两个，失败后无法归因。
4. **可复现 > 有解释**。先拿到稳定复现，再谈根因。

## 固定输出四段

```markdown
### 1. 当前证据（只列实测）
- 实测：DQ 收尾阶段返回 X，时间戳 T1（来源：日志 2026-11-12_1530.log:行号）

### 2. 假设（按可能性排序，带置信度）
- H1 [高] DQ 收尾状态机缺少超时兜底 → 证伪实验：注入 5s 延迟看是否仍卡死
- H2 [中] 上电时序导致 DQ 首帧异常 → 证伪实验：冷启动 3 次取首帧
- H3 [低] 连接器接触不良 → 证伪实验：替换线束后重复 10 次

### 3. 下一步动作（≥3 条，按信息增益排序）
每条必须写：怎么做 / 看什么 / 现象 A 说明什么 / 现象 B 说明什么

### 4. 未决项与所需输入
- 需要你提供：完整 DQ 收尾阶段日志（从第一条异常到 SAFE 触发之间的全部行）
```

## 分支化（强制）

结论写成 if/then 树，不要给单点：

```
如果复现（同现象）
  ├─ 且换线束仍复现 → 指向软件/时序（H1 或 H2）
  └─ 且换线束不复现 → 指向接触/线束
如果不复现
  └─ 记录环境差异（温度/电压/上电顺序），转为偶发问题，加大样本
```

**若两个分支现有信息无法区分，直接写："区分 A 与 B 需要观测 X，获取方式是 Y"。**

## 硬件排查的额外要求

- 记录环境：温度、供电电压、上电顺序、固件版本、板号。
- 先量后猜：能用万用表/示波器/协议分析仪确认的，不靠推理。
- 区分"确定性缺陷"与"偶发缺陷"：偶发要先建立复现率，再谈根因。
- 换件实验必须一次性只换一件。

## 收尾自检

- 这轮排查让信息量增加了吗？
- 结论里哪些是推断？标了吗？
- 下一个接手的人，能凭这份记录直接动手吗？
