# 排查铁律

> 完整流程见 `agent/playbooks/30-debug.md`。这里是**约束**，违反即返工。

## 五条铁律

1. **交付是「下一步动作」，不是「结论」**。禁止以「证据不足，无法确定」收尾。
2. **一次只改一个变量**。同时动两个，失败后无法归因。
3. **可复现 > 有解释**。先拿稳定复现，再谈根因。
4. **先查历史**。同类现象可能已归档：先搜 `agent/context/archive/` 与 `agent/context/decisions.md`，避免重做同一批实验。
5. **区分「已绕过」与「已修复」**。绕过必须标 `workaround` 并留复验条件。

## 证伪优先

每个假设配一个**能否证伪**的实验：

- 好：「替换线束后重复 10 次，若仍复现 → 指向软件」
- 坏：「再观察看看」

不能证伪的假设，不写进假设清单。

## 硬件排查的额外约束

- 记录环境：温度、供电电压、上电顺序、固件版本、板号。
- 先量后猜：万用表 / 示波器 / 协议分析仪能确认的，不靠推理。
- 偶发缺陷先建立复现率（N 次里几次），再谈根因。
- 换件实验一次只换一件。

## 结论的可信度

| 表述 | 允许的前提 |
| --- | --- |
| 「已修复」 | 有复现用例，且修复后该用例通过 |
| 「已绕过」 | 有规避动作 + 未验证根因 + 复验条件 |
| 「疑似」 | 有证据链但缺直接观测 |
| 「无法确定」 | **不允许单独出现**，必须紧跟取证计划 |

## 反模式

- ❌ 把「换个线就好了」当成根因分析。
- ❌ 复现不了就直接判「偶发，无解」。
- ❌ 一轮里同时改配置、换硬件、升级固件。
- ❌ 结论不写环境（换台机器就失效的结论等于没结论）。
