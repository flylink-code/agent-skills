# 多工程隔离

常规项目通常是「一个 `doc/` + 多个工程目录」。这些工程**互相独立**：各自编译、各自版本、各自负责人。

## 三层结构

| 层 | 位置 | 放什么 | 谁可写 |
| --- | --- | --- | --- |
| 工作区 | `AGENTS.md`、`agent/` | 跨工程事实：需求、客户、共享规范、决策 | 人 + Agent（需理由） |
| 工程 | `projects/<工程>/` | 该工程的路由、规则覆盖、事实卡 | 该工程的 Agent |
| 共享资料 | `doc/` | 需求、原理图、会议记录、标准 | 人；Agent 只读 |

## 铁律

1. **默认只读他工程**。要改别的工程，先说明理由、取得同意、记录到 `agent/context/decisions.md`。
2. **工程内 `agent/` 自包含**。不引用别的工程的 rules/context 文件，各工程规则可不同。
3. **不假设同构**。端口、数据库、配置键、协议版本都可能不同；引用前先看该工程的 `agent/context/software.md`。
4. **不改共享层去迁就单个工程**。共享规范变更必须评估对所有工程的影响。
5. **代码地图按工程各建一份**（`projects/<工程>/doc/CODE_MAP_INDEX.md`），不建全局大图。

## 跨工程任务怎么做

```
1. 明确边界：涉及哪几个工程？各自负责什么？
2. 分别读各工程 AGENTS.md + context/software.md
3. 接口约定写进工作区 agent/context/decisions.md（谁调用谁、字段、版本）
4. 改动分工程提交，一次一个工程，便于回滚
5. 联调结果写进工作区 plan.md，不写进单个工程
```

## 判断「这是不是同一个工程」

| 现象 | 结论 |
| --- | --- |
| 各自有 `.git` | 独立工程 |
| 各自有构建脚本 / 依赖清单 | 独立工程 |
| 共享一个 `doc/` 但代码目录平级 | 独立工程（常见形态） |
| 同一编译单元里的多模块 | 一个工程，用 code-map 的 `modules` 区分 |

## 反模式

- ❌ 在 A 工程里「顺手」修 B 工程的 bug —— 无法回滚，评审看不到。
- ❌ 把 A 工程的端口/路径假设套到 B 工程。
- ❌ 把某工程的调试结论写进共享 `decisions.md` —— 它只对那个工程成立。
- ❌ 在共享层写「所有工程都这样」而没有验证过全部工程。
