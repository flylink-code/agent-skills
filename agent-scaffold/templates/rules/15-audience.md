# 受众与措辞

产物里的字只写给它的**最终读者**，不写给请求者。Agent 与请求者之间的对话痕迹不得留在代码、界面和文档里；要对请求者说的话，放在本轮回复里。

## 先判断读者是谁

| 位置 | 读者 | 该写什么 |
| --- | --- | --- |
| UI 文案 / 提示 / 报错 | 最终用户 | 产品语言：发生了什么、现在能做什么 |
| 代码注释 | 后来的维护者 | 意图、约束、为什么不那样写、坑在哪 |
| README / 设计文档 | 使用者 / 集成者 / 开发者 | 按 `rules/30-docs.md` 的 Diátaxis 定读者，一份文档只服务一类 |
| TODO / FIXME | 接手的开发者 | 代码层面的待办事实与触发条件 |
| 测试名 / 日志 | 排查的人 | 被测行为、现象，不写「用户要的」 |
| 提交信息 | 评审与回溯的人 | 为什么改（见 `rules/20-git.md`） |

## 禁用：对话痕迹

| 不要写 | 改写为 |
| --- | --- |
| 按照你的要求启用自动连接 | 自动连接 |
| 这里修改为异步加载 | 异步加载图片资源，避免阻塞界面线程 |
| 用户要求增加重试功能 | 网络请求失败时自动重试 |
| 这个按钮用于你配置参数 | 配置参数 |
| TODO: 后续按照用户需求完善 | TODO: 补充连接超时处理 |
| `// per your request, disable TLS` | `// Pin the device certificate; the server certificate is self-signed` |
| `as requested` / `as discussed` / `按需求实现` / `根据你说的` | 直接陈述行为或原因 |

同时不要：在注释里复述对话（"如上所述"）、把承诺写进产物（"后续会补"）、把模型自己的思考过程写进代码、在产品文案里出现"用户 / 你 / 请求 / 需求方"。

## 收尾必做

提交前扫一遍**新增或改动**的 UI 串、注释、文档、TODO，命中上表就改写成陈述句：

```powershell
git diff -U0 | Select-String -Pattern '你的要求|你的需求|用户要求|按需求|按照.*要求|as requested|per your request|as discussed'
```

请求者要的解释、变更说明、风险提示写在**回复**里，不进产物。

## 反模式

- ❌ 「按用户要求先写死」——可以写死，但要写清为什么现在写死、什么条件下改。
- ❌ 给「下一轮对话」留 TODO——TODO 只记代码事实，不记会话计划。
- ❌ 在注释里写「已修复 / 已验证」——状态属于提交信息与 `plan.md`，且必须诚实（`rules/00-global.md`）。
