# 阶段一：创建 / 立项

目标：把一个模糊的「要做个东西」变成**可执行、可验收、有依据**的方案。

## 步骤

```
Task Progress:
- [ ] Step 1: 澄清要解决的真实问题
- [ ] Step 2: 查本地已有（需求 / 决策 / 归档 / 调研）
- [ ] Step 3: 网上调研（≥3 个独立来源）
- [ ] Step 4: 方案对比（≥2 个，写取舍）
- [ ] Step 5: 定接口与边界
- [ ] Step 6: 写验收标准与里程碑
- [ ] Step 7: 落卡（4 张事实卡 + 1 张调研卡）
```

### Step 1: 澄清

必须先拿到这五项，缺哪项就问哪项（一次问完，不要挤牙膏）：

1. 谁在用、什么场景、现在怎么解决的
2. 成功长什么样（可量化）
3. 硬约束：成本、周期、平台、认证、产线节拍
4. 明确不做什么
5. 谁拍板

**不要**在缺 1、2 项的情况下直接给技术方案。

### Step 2: 查本地

- `agent/context/requirements.md`：需求有没有变过
- `agent/context/archive/`：是不是已经做过、当时为什么停
- `agent/context/research/`：调研过没有
- `agent/context/decisions.md`：有没有相关取舍

命中已归档的同类方案 → 先读结论，**不要从头再来**。

### Step 3: 网上调研

按 `agent/rules/50-research.md` 执行。产出写 `agent/context/research/<主题>.md`。

最低要求：

- ≥3 个独立来源，含至少 1 个官方文档/规范
- 至少 1 条「失败案例 / 不适用场景」
- 每条结论带 URL 与访问日期

### Step 4: 方案对比

至少两个方案，同一个评分维度表：

| 维度 | 方案 A | 方案 B |
| --- | --- | --- |
| 满足需求 | | |
| 实现成本 | | |
| 维护成本 | | |
| 风险（技术/供应/许可） | | |
| 可回退性 | | |

**必须有「放弃的方案 + 理由」**，只写推荐方案等于没做过对比。

### Step 5: 接口与边界

写清楚：

- 对外接口：字段、单位、频率、错误码
- 与既有系统的边界：谁调用谁、谁负责重试
- 多工程时：哪个工程负责哪一段（见 `agent/rules/70-isolation.md`）

### Step 6: 验收与里程碑

每条验收标准必须可判定：

- 好：「600 Mbps 下连续 8 小时无 DQ 超时」
- 坏：「稳定性良好」

里程碑给日期与交付物，不给「大概下个月」。

### Step 7: 落卡

| 写到哪 | 写什么 |
| --- | --- |
| `agent/context/requirements.md` | 范围、指标、验收、事实源指针 |
| `agent/context/software.md` | 架构与接口（若已定） |
| `agent/context/decisions.md` | 选型取舍 |
| `agent/context/research/<主题>.md` | 调研记录 |
| `agent/context/plan.md` | 里程碑与当前状态 |

## 完成判据

- 一个没参与讨论的人，只看这几张卡，能说出「做什么、不做什么、怎么算完成、为什么这么选」
- 调研卡里否掉的方案有理由
- `plan.md` 里第一项能立刻开工

## 反模式

- ❌ 需求没定就画架构图。
- ❌ 只调研到「网上有人说可以」。
- ❌ 方案只有一种（那不是对比，是辩护）。
- ❌ 验收标准写成「客户满意」。
