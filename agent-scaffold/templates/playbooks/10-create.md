# 阶段一：创建 / 立项

目标：把一个模糊的「要做个东西」变成**可执行、可验收、有依据**的方案。

## 步骤

```
Task Progress:
- [ ] Step 1: 澄清要解决的真实问题
- [ ] Step 2: 查本地已有（需求 / 决策 / 归档 / 调研）
- [ ] Step 3: 依据风险和证据缺口决定是否补查外部资料
- [ ] Step 4: 说明选型依据，有可行替代方案时比较取舍
- [ ] Step 5: 定接口与边界
- [ ] Step 6: 写验收标准与里程碑
- [ ] Step 7: 更新相关事实卡，有可复用的调研结论时登记调研卡
```

### Step 1: 澄清

必须弄清这五项。1、2 只有用户知道，缺了就一次问完，不要挤牙膏；3~5 先查 `agent/context/` 与 `docs/`
推断，给假设并在答复里标注，推断不出来的再一起问（`rules/00-global.md`「推进与停止条件」）。

1. 谁在用、什么场景、现在怎么解决的
2. 成功长什么样（可量化）
3. 硬约束：成本、周期、平台、认证、产线节拍
4. 明确不做什么
5. 谁拍板

**不要**在缺 1、2 项的情况下直接给技术方案。

### Step 2: 查本地

- `agent/context/requirements.md`：需求有没有变过
- `agent/context/archive/`：是不是已经做过、当时为什么停
- `agent/context/research/`：调研过没有
- `agent/context/decisions.md`：有没有相关取舍

命中已归档的同类方案 → 先读结论，**不要从头再来**。

### Step 3: 网上调研

已有依据足以支持低风险决定时直接进入方案选择。遇到证据缺口、版本变化或高风险取舍，按 `agent/rules/50-research.md` 补查，记录采信的来源、版本和适用条件。

### Step 4: 方案对比

存在可行的替代方案时，可按同一组维度比较。若只有一种路径符合硬约束，说明决定选择的约束即可。

| 维度 | 方案 A | 方案 B |
| --- | --- | --- |
| 满足需求 | | |
| 实现成本 | | |
| 维护成本 | | |
| 风险（技术/供应/许可） | | |
| 可回退性 | | |

记录推荐理由，以及实际考虑过哪些替代方案、为什么放弃。

### Step 5: 接口与边界

写清楚：

- 对外接口：字段、单位、频率、错误码
- 与既有系统的边界：谁调用谁、谁负责重试
- 多工程时：哪个工程负责哪一段（见 `agent/rules/70-isolation.md`）

### Step 6: 验收与里程碑

每条验收标准必须可判定：

- 好：「600 Mbps 下连续 8 小时无 DQ 超时」
- 坏：「稳定性良好」

里程碑给日期与交付物，不给「大概下个月」。

### Step 7: 落卡

| 写到哪 | 写什么 |
| --- | --- |
| `agent/context/requirements.md` | 范围、指标、验收、事实源指针 |
| `agent/context/software.md` | 架构与接口（若已定） |
| `agent/context/decisions.md` | 选型取舍 |
| `agent/context/research/<主题>.md` | 调研记录 |
| `agent/context/plan.md` | 里程碑与当前状态 |

## 完成判据

- 一个没参与讨论的人，只看这几张卡，能说出「做什么、不做什么、怎么算完成、为什么这么选」
- 调研卡里否掉的方案有理由
- `plan.md` 里第一项能立刻开工

## 反模式

- ❌ 需求没定就画架构图。
- ❌ 只调研到「网上有人说可以」。
- ❌ 为了凑对比表，列出不满足硬约束的候选方案。
- ❌ 验收标准写成「客户满意」。
