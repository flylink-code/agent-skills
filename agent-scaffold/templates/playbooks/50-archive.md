# 阶段五：归档 / 交接

目标：让**下一个 Agent** 不重做、不误用、能接手。归档质量 = 后来者的效率。

## 什么时候归档

- 缺陷已修复且回归通过
- 需求已交付验收
- 阶段收敛、换人、结项
- 方案被取代

**不归档**：根因未定只有绕过（标 `workaround` 留活跃区）、还在观察期的偶发问题。

## 五步

```
Task Progress:
- [ ] Step 1: 定稿结论（含证据与 commit）
- [ ] Step 2: 写归档卡（含「不要再做」与「失效条件」）
- [ ] Step 3: 移入 archive/ 并改 status
- [ ] Step 4: 登 ARCHIVE_INDEX.md
- [ ] Step 5: 清理活跃区（plan / index / AGENTS）
```

### Step 1: 定稿

先提交代码与文档，拿到 commit 号。归档卡里的 `commit:` 必须指向**归档时的代码状态**，否则以后无法还原。

结论必须回答：根因是什么 / 怎么修的 / 怎么验证的 / 还剩什么没解决。

### Step 2: 归档卡

按 `agent/rules/60-archive.md` 的结构写。三件事必须有：

1. **证据**：复现用例、修复前后对比、环境。
2. **不要再做**：做过且无效的尝试（这是最省后来者时间的一段）。
3. **失效条件**：什么情况下这个结论作废（换板、换固件、改采样率、改协议）。

### Step 3: 移入归档区

`agent/context/archive/<主题>.md`。只移动，不销毁；原文保留。
frontmatter：`status: archived`、`archived:`、`commit:`、`superseded_by:`、`valid_until:`。

### Step 4: 登索引

`ARCHIVE_INDEX.md` 一行：主题 / 结论一句话 / 状态 / 失效条件 / 路径。

一句话要能让读者决定「要不要点进去」。

### Step 5: 清理活跃区

| 文件 | 清理动作 |
| --- | --- |
| `agent/context/plan.md` | 删已完成项，保留下一步 |
| `agent/index.md` | 移除已失效触发条件 |
| `agent/AGENTS.md` | 若某条已固化成规则并长期有效，移出路由噪音 |
| `agent/context/software.md` | 更新为当前真实状态 |

**不清理 = 下次又被排进待办 = 归档白做。**

## 交接包（换人时）

一个新人拿到这些就能接手：

1. `AGENTS.md`（怎么找东西）
2. `agent/context/plan.md`（现在到哪了）
3. `ARCHIVE_INDEX.md`（哪些已经做完，别重做）
4. `decisions.md`（为什么这么定）
5. 最近 3 次提交（现状从哪来）

## 完成判据

- 新会话只读这 5 份，能说出「现在该干什么、哪些不能碰」
- 归档卡里「不要再做」≥1 条（没有说明没排查过）
- 失效条件明确
- 活跃区里没有已完成项残留

## 反模式

- ❌ 归档＝把文件夹拖进 archive/。
- ❌ 归档卡只写「已完成」。
- ❌ 不记 commit 号。
- ❌ 归档后不清理 plan.md。
- ❌ 把 workaround 当已修复归档（最危险：后来者以为根因已解决）。
