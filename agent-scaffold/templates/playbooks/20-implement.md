# 阶段二：实现 / 编码

目标：**小步、可验证、可回滚**地把方案变成代码。

## 步骤

```
Task Progress:
- [ ] Step 1: 确认当前任务与验收标准（读 plan.md + requirements.md）
- [ ] Step 2: 用 code-map 定位，读懂上下游
- [ ] Step 3: 拆成可独立验证的小步（每步 ≤ 半个工作日）
- [ ] Step 4: 写代码 + 就地自测
- [ ] Step 5: 跑测试 / 最小可执行路径
- [ ] Step 6: 提交（一个提交一件事）
- [ ] Step 7: 更新卡与进度
```

### Step 1: 对齐

开工前先答：

- 这一步的验收标准是什么？
- 改完之后谁受影响（接口 / 协议 / 产线）？
- 失败怎么回滚？

答不上来先别写代码。

### Step 2: 定位

```powershell
node doc/codemap.mjs --find <符号>      # 声明与引用
node doc/codemap.mjs --outline <文件>   # 文件结构
```

拿不到就说明地图过期 → 先 `--map` 重建，再动手。

### Step 3: 拆步

每步满足：能单独提交、能单独验证、失败能单独回退。
拆不动的部分（大重构）单独开分支，先立基线再动。

### Step 4: 写

- 跟随既有风格，不引入新的范式。
- 边界条件先写（空、超时、断电、越界）。
- 日志留在能定位问题的粒度：入口、异常分支、状态跃迁。
- 写给最终读者：UI 文案面向用户，注释面向维护者，**不写**「按你的要求」「用户要的」（`agent/rules/15-audience.md`）。
- 不在这一步顺手改无关代码。

### Step 5: 验

| 层次 | 做什么 |
| --- | --- |
| 单点 | 目标函数/模块的输入输出 |
| 集成 | 与该模块相邻的一层 |
| 真机 | 上板 / 上产线，至少走一遍主流程 |

跑不了就写清「未跑，原因 + 风险」，**不要**写「应该没问题」。

### Step 6: 提交

按 `agent/rules/20-git.md`。提交信息写「为什么」，不是「改了什么」。

### Step 7: 更新

- `agent/context/plan.md`：完成项移到已完成，写新的下一步
- `agent/context/software.md`：接口/模块变化
- `agent/context/decisions.md`：重大取舍

## 完成判据

- 每一步都有独立的验证证据（日志/测试/截图）
- 新增的 UI 串、注释、TODO、文档没有对话痕迹（按 `agent/rules/15-audience.md` 的禁用语表扫一遍）
- 任何一步失败都能单独回退
- 新会话读 `plan.md` 能接着干

## 反模式

- ❌ 一次改 10 个文件再一起跑。
- ❌ 改完不跑就说完成。
- ❌ 边写边改需求（需求变了先回 Step 1 记录变更）。
- ❌ 把调试用的临时代码留在提交里。
